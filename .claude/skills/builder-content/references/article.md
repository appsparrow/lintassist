# Medium-style article (builder's view)

**Length:** 900–1,400 words. First person. Subheadings every 150–200 words.

## Structure
1. **Title.** A claim, not a topic. ("You don't need a title to build a product. You need to be ready to solve problems.")
2. **Dek.** One italic sentence on what the reader will learn.
3. **Opening (3–4 sentences).** The question or tension that started it, in the user's own words where possible.
4. **Numbered sections** (pick the ones the project's facts support, in this order):
   1. A problem that repeats all week deserves a weekend (persistence, the idea that kept returning)
   2. Start from a use case, not a technology
   3. The first version is a prototype of the idea (prompt/spec refinement, iteration)
   4. Every wall is a design decision in disguise (2–4 real blockers and what each forced)
   5. Design the access model like a product (free tier, limits, trust, what was held back)
   6. One backend/foundation makes every new surface cheap (how the later channel came fast)
   7. Hold your own work to the standard you sell (self-review)
   8. Shippable means more than working (PRD, docs, release notes, security answers, marketing, admin)
5. **"What I'd tell anyone who wants to do this."** A numbered list of 8–10 one-line takeaways.
6. **Closing line** with the broader point (designers, developers and AI builders converging on owning zero-to-one).
7. **Footer line.** One italic line naming the project, only if the reveal level allows.

## Rules
- Each wall/blocker must be real (from git history, docs or the user). No invented war stories.
- State the AI/human split honestly, as the user described it, with "roughly".
- Include a short list of the non-code artifacts that made it shippable.
- Keep jargon explained in a clause. The reader may be a designer, PM or engineer.
- Offer to add a "what I'd do differently" section if the user wants more reflection.
